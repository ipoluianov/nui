# Что проверить на Windows и macOS

Код, который на Linux проверен вживую, а на Windows и macOS только компилируется. Для каждого пункта указаны: что сделать, что должно получиться и какой код под подозрением, если результат другой.

Как отчитываться: отметить пункт `[x]` или записать, что получилось на самом деле. Приложить скриншоты окна `fontcheck` и вывод программы в консоль. Версию ОС и масштаб экрана указать один раз в начале раздела платформы.

## Шрифты: начертания, системные шрифты, синтез

Что изменилось:
- у встроенных Noto Sans и JetBrains Mono появились Bold, Italic и Bold Italic;
- у виджетов и Canvas появились `SetFontBold` и `SetFontItalic`, стиль можно записать в имени семейства: `"notosans:bold"`;
- неизвестное имя семейства ищется среди системных шрифтов;
- начертание, которого у шрифта нет, синтезируется.

### Подготовка

```
go test ./ui ./internal/platforms
go run ./cmd/fontcheck            # интерфейс встроенным Noto Sans
go run ./cmd/fontcheck -system    # интерфейс системным шрифтом (UseSystemFont)
```

**Окно `fontcheck`** показывает четыре начертания для каждого семейства:
- шрифт темы (в окне подписан `theme font: …`);
- `notosans`, `jetbrainsmono`;
- `goregular` — зарегистрирован только Regular, остальное синтезируется;
- три системных шрифта:

  | ОС | Со всеми начертаниями | Без жирного и курсива | Шрифт интерфейса |
  |---|---|---|---|
  | Windows | Times New Roman | MS Gothic | `SystemUIFontName()` |
  | macOS | Helvetica Neue | Apple Chancery | `SystemUIFontName()` |

- несуществующий шрифт `No Such Font 123`.

Ниже в окне — курсив 40 px и TextBox в JetBrains Mono Bold Italic.

**В консоль программа печатает таблицу ширин** образца из 39 символов при 15 px, затем ту же таблицу для образца без `中文` (36 символов): строку с символом, которого нет в шрифте, GDI не рисует, и встроенные шрифты проверяются через GDI только по второй таблице:
- `native` — ширина через текстовый движок системы (GDI на Windows);
- `nui` — ширина через собственный растеризатор nui;
- `native-regular` — разница с обычным начертанием того же семейства.

**Как отличить настоящее начертание от синтезированного.** Синтезированный жирный шире обычного **ровно на 1 px на символ**, то есть `native-regular` = 39 (или очень близко к 39). У настоящего жирного разница другая. Например, на Linux:

| Начертание | `native-regular` |
|---|---|
| `notosans:bold` | 23 |
| `DejaVu Serif:bold` | 31 |
| `goregular:bold` (синтез) | 39 |
| `jetbrainsmono:bold` | 2 (моноширинный: настоящий жирный той же ширины, +2 дают синтезированные жирные иероглифы `中文`) |

**Как отличить настоящий курсив от наклонённого прямого шрифта** — по кириллице в слове «датский тариф»:
- в настоящем курсиве Noto Sans «д» похожа на «g», «т» — на «m», «и» — на «u»;
- в синтезированном это прямые буквы с наклоном.

### Windows

Особенность Windows: встроенные шрифты и шрифты из `RegisterFont` по умолчанию рисуются через GDI с ClearType (`NativeFontRendering = true`). Каждое начертание передаётся GDI отдельно ([systemfontdata_windows.go](../internal/platforms/systemfontdata_windows.go)). GDI различает начертания по имени семейства, весу (400/700) и признаку курсива. В наших файлах всё это задано правильно, проверено по таблицам OS/2 и name.

- [x] **GDI рисует настоящий жирный, а не синтезирует его из Regular.**
  - У `notosans:bold` колонки `native` и `nui` близки: расхождение в несколько пикселей из-за хинтинга допустимо.
  - `native-regular` заметно меньше 39.
  - Если в `native` разница около 39, GDI синтезирует жирный сам, и надо смотреть `registerFontData` и `fontDataInfo`.
  - Windows 11 (10.0.26300), 100%: в образце с `中文` колонка `native` у встроенных шрифтов GDI не проверяет: строку с символом, которого нет в шрифте, целиком рисует растеризатор nui (`hasAll` в `systemFontFor`). Поэтому `fontcheck` печатает вторую таблицу, без `中文`. По ней: `notosans:bold` +21 из 36, `notosans:bold:italic` +11, `jetbrainsmono:bold` 0 — настоящие начертания. Колонки `native` и `nui` совпадают до пикселя. Что работает именно GDI (`windowsFont`), проверено отдельно.
- [x] **ClearType работает во всех начертаниях.** При увеличении скриншота у букв обычного и жирного начертания видны цветные края (субпиксельное сглаживание).
  - Windows 11, 100%: у текста, который рисует GDI, есть (TextBox JetBrains Mono Bold Italic, курсив 40 px, Segoe UI). У строк встроенных шрифтов с `中文` ClearType нет: их рисует растеризатор nui, в оттенках серого. Это видно и в приложении: строка с одним иероглифом или эмодзи выглядит иначе соседних (см. «Найдено на Windows», п. 3).
- [x] **У системных шрифтов колонки `native` и `nui` совпадают.** Системные шрифты всегда рисует GDI, переключатель `NativeFontRendering` на них не влияет.
- [x] **Times New Roman — настоящие начертания.** `native-regular` у Bold не 39; курсив рукописный («д» как «g», «т» как «m»).
  - Windows 11, 100%: Bold +31, Italic +20, Bold Italic +34; курсив рукописный.
- [x] **MS Gothic — жирный и курсив синтезирует GDI.** Bold заметно жирнее, Italic наклонён, `native-regular` у Bold около 39.
  - Windows 11, 100%: Bold +39, Italic 0, наклонён.
- [x] **Шрифт интерфейса (обычно Segoe UI)** — четыре разных начертания.
  - Windows 11, 100%: Bold +18, Italic +11, Bold Italic +37. Bold Italic близко к 39, но это настоящий `segoeuiz.ttf`: ширины совпадают с посчитанными по файлам (270/286/281/305 без `中文`).
- [x] **Курсив, нарисованный через GDI, не обрезан.** GDI рисует текст в битмап с запасом по краям; запас теперь 3 px плюс четверть высоты букв ([systemtext_windows.go](../internal/platforms/systemtext_windows.go), `Draw`). Проверить курсив 40 px и последние буквы строк Italic у Times New Roman и Segoe UI.
- [ ] **Noto Sans, установленный в систему.** Если на машине установлен Noto Sans, при запуске с ним нужно убедиться, что жирный и курсив по-прежнему выглядят правильно. GDI видит два шрифта с одним именем: наш, загруженный в память, и системный. Какой из них он выберет, заранее неизвестно.
- [ ] **Масштаб 150% и 200%.** Повторить проверку настоящего жирного и курсива при другом масштабе в настройках Windows.

### macOS

Особенность macOS: системные шрифты рисует не CoreText, а растеризатор nui. CoreText только находит файл нужного начертания ([systemtext_darwin.go](../internal/platforms/systemtext_darwin.go), `SystemFontFile`):
1. берёт шрифт по имени;
2. через `CTFontCreateCopyWithSymbolicTraits` получает жирное или курсивное начертание;
3. возвращает путь к файлу и PostScript-имя.

Начертание выбирается из `.ttc` по PostScript-имени (`openFontFile` в [font_system.go](../ui/font_system.go)). Если в файле нет начертания с таким именем, оно синтезируется из Regular.

- [x] **`-system` и `SetFontFamily("Helvetica Neue")` вообще работают.** До этой правки `UseSystemFont` на macOS требовал, чтобы в шрифте были китайские иероглифы, и для Helvetica Neue или SF возвращал ошибку. Ожидается: ошибки нет, текст нарисован системным шрифтом (отличается от `notosans`).
- [x] **Helvetica Neue — настоящие начертания из `.ttc`.** Сначала не работало: `nui: no font "Helvetica Neue"` — в `HelveticaNeue.ttc` у основных начертаний только таблица `cmap` Unicode 1.1 (платформа 0, кодировка 1), а `x/image/font/sfnt` её не берёт (`unsupported cmap encodings`). Теперь файл читается с этой кодировкой, поданной как Unicode BMP (3), формат таблицы тот же (`cmapEncodingPatches` в [font_system.go](../ui/font_system.go)); тест `TestHelveticaNeue`. macOS 27.0.1, Retina: Bold +19, Bold Italic +17 — настоящие начертания. `native-regular` у Bold не 39, Bold Italic отличается от Bold. Если все четыре строки одинаковые, CoreText не нашёл начертания или `openFontFile` взял первый шрифт коллекции.
- [x] **Шрифт интерфейса (SF) — жирный не нарисован как обычный.** macOS 27.0.1, Retina: `.AppleSystemUIFont:bold` +39 (синтез). SF — вариативный шрифт: жирное начертание лежит в том же файле как экземпляр вариаций. Растеризатор nui вариации не применяет, поэтому такой жирный должен синтезироваться.
  - Ожидается: Bold заметно жирнее, `native-regular` около 39.
  - **Плохой результат:** Bold совпадает с Regular (`native-regular` = 0).
- [x] **Apple Chancery — синтез из Regular.** macOS 27.0.1, Retina: Bold +19, а не 39: кириллицы и `中文` в шрифте нет, их рисуют запасные шрифты со своим настоящим жирным; синтезируется только латиница. Bold около 39. Вместо кириллицы и `中文` могут быть квадратики, если в шрифте нет этих символов. Это отдельное ограничение, см. последний пункт.
- [x] **Retina.** Текст всех начертаний чёткий, курсив не «лесенкой».
- [x] **Иероглифы.** `中文` рисуется системным китайским шрифтом (PingFang), в жирных строках — синтезированным жирным.
- [x] **Нет fallback для символов, кроме китайских, японских и корейских** (ожидаемо, но стоит подтвердить). Подтверждено: ⌫ ★ ✓ — квадратики; JetBrains Mono теперь даёт ⌘ ⇧ ⌃ ⌥, стрелки и √. Описано в ограничениях, [fonts.md](ui/content/fonts.md#limitations). Если у системного шрифта нет кириллицы, nui не ищет её в других системных шрифтах: на Linux это делает fontconfig, на macOS такого механизма нет. Если подтвердится — это пункт в план (fallback для символов и эмодзи, P1 в [production-readiness.md](production-readiness.md)).

## Слой приложения (фаза 6): Activate, состояние окна, одна копия

Проверено без дисплея и на Linux; на Windows и macOS — только сборка.

### Windows

Windows 11 (10.0.26300), 100%, один монитор. Проверено программой с `AcquireSingleInstance`, `RememberState` и `OnActivate` → `Activate`; окно сворачивалось и разворачивалось через `ShowWindow`, состояние читалось `IsIconic`, `IsZoomed`, `GetWindowPlacement`.

- [x] **`Activate`** (`ui/activate_windows.go`): свернуть окно, вызвать `form.Activate()` (например, вторым запуском приложения с `AcquireSingleInstance`): окно разворачивается из панели задач и становится активным; развёрнутое на весь экран остаётся развёрнутым; окно под другими выходит наверх (Windows может только мигать кнопкой в панели задач, если процесс не в фокусе — второй запуск зовёт `AllowSetForegroundWindow`, это должно помогать).
  - Свёрнутое окно после второго запуска развёрнуто и на переднем плане; свёрнутое из развёрнутого снова развёрнуто на весь экран.

Сокет — AF_UNIX (Windows 10 1803+): на более старой системе второй запуск не сможет показать первый, но и не запустится второй копией.
  - Аргументы `"a b"` и `--x=ä` дошли без изменений; после выхода первого новый запуск становится первым.
- [ ] **`RememberState`**: развернуть окно, закрыть, открыть снова — окно развёрнуто, а после «Восстановить» — прежнего обычного размера. С двумя мониторами: закрыть окно на втором, отключить его, открыть — окно на первом.
  - Один монитор: работает после исправления «Найдено на Windows», п. 2. До него после «Восстановить» окно было почти во весь экран или меньше прежнего на рамку и в другом месте. Два монитора не проверены.

### macOS

- [x] **`Activate`**: окно, свёрнутое в Dock, выходит из него; приложение становится активным.
  - macOS 27.0.1, Retina: после `Minimize` и `Activate` окно снова на экране и на прежнем месте. Проверено программой, без щелчков.
- [x] **`AcquireSingleInstance`**: как на Windows (сокет в `~/Library/Application Support/<app>`).
  - macOS 27.0.1, Retina: второй запуск передал первому `["a.txt" "b c.txt"]` и вышел.
- [x] **`RememberState`**: как на Windows; координаты окна на macOS считаются от другого угла экрана — проверить, что окно открывается на прежнем месте, а не отражённым по вертикали.
  - [x] Место: окно в (200, 150) → `State` → новое окно из этого состояния открылось в (200, 150), на экране его угол тоже в 200, 150 сверху. Не отражено.
  - [x] **Размер развёрнутого окна — исправлено.** Было: После `Maximize` `State()` вернул `Width:1260 Height:709`, а должен вернуть обычный размер 500×350, к которому окно возвращает `Restore`. `RememberState` поэтому сохраняет размер на весь экран, и после перезапуска «Восстановить» окно не уменьшает. Вероятная причина: `zoom:` на macOS анимируется, события ресайза приходят, пока `isZoomed` ещё false, и `rememberNormal` ([formstate.go](../ui/formstate.go)) записывает промежуточные размеры как обычные. Исправлено: делегат `windowShouldZoom:toFrame:` помечает окно как разворачиваемое, и до конца анимации `IsMaximized` возвращает true. Теперь `State()` развёрнутого окна — `500×350`, `Maximized: true`.
- [ ] **Баг #13, отложен:** `ShowModal` на macOS блокирует до закрытия диалога (`runModalForWindow`), на Windows и Linux — нет. Код, построенный на обработчиках результата (все диалоги nui), работает на обеих; проверить, что диалоги nui на macOS открываются и закрываются, а окно под ними не принимает ввод. Неблокирующий вариант — модальная сессия Cocoa (`beginModalSessionForWindow`), без машины с macOS не делался.
  - [x] macOS 27.0.1, вручную в notepad (Find, Go To Line): окно под диалогом не принимает ввод и не закрывается, после закрытия диалога работает с первого щелчка. Блокирующий вызов остаётся (сам баг #13), для пользователя поведение правильное.

## Окно macOS: отрисовка, фон, потоки, размер, печать

Это изменения, включённые у всех по умолчанию. Автоматические тесты на macOS проходят (`go test ./...`), но они рисуют без настоящего окна.

- [x] **Кадр рисуется без артефактов.** Каждый `drawRect` теперь копирует буфер кадра в `CFData` (`newCGImageRGBA` в [cocoa_darwin.go](../internal/platforms/cocoa_darwin.go)). Раньше CoreGraphics читал память Go напрямую.
  - Ресайз большого окна на Retina плавный, нет мерцания и мусора по краям.

## Частичная перерисовка (все ОС)

Буфер окна теперь хранит прошлый кадр. Кадр перерисовывает поверх него только прямоугольники изменившихся виджетов, а фон заливает форма, не платформа (`windowPaint` на macOS, `paint` на Linux, `WM_PAINT` на Windows). Вывод на экран прежний: весь буфер. Подробно — в [testing.md](testing.md), раздел «Частичная перерисовка».

Как проверять: запускать примеры с `NUI_CHECK_REPAINT=1` и смотреть в консоль. Каждая строка `nui: repaint check: …` — найденная ошибка; в ней указаны область и виджеты.

- [ ] **Следов старой картинки нет.** В лаунчере, gallery, notepad, contacts, cad, chartgallery, viewer3d, monitor водить мышью, крутить колесо, перетаскивать, открывать меню и списки, менять размер окна, сворачивать и разворачивать, перекрывать окно другим. В консоли нет `repaint check`, на экране нет следов подсветки, курсора, перекрестья, подсказок.
  - macOS 27.0.1, Retina, автоматически: `TestRepaintMonkey` (все примеры, масштабы 1, 1,5 и 2) и viewer3d с автоповоротом в настоящем окне с `NUI_CHECK_REPAINT=1`. Расхождений нет, 99% кадров частичные. Мышью вручную не проверялось.
- [ ] **Фон окна.** Там, где виджетов нет (край окна при ресайзе, пустая форма), фон цвета темы, в светлой и тёмной. Раньше на Linux буфер заливался с переставленными R и B.
- [ ] **Окно после перекрытия и сворачивания** рисуется целиком: такой кадр система запрашивает сама, и форма рисует его полностью.

Его закрытие вызывает `quitApp` → `[NSApp terminate:]` ([utils_darwin.go](../internal/platforms/utils_darwin.go), `go_on_window_will_close`), то есть `exit` процесса. На Linux и Windows `form.Exec()` ждёт закрытия своей формы и возвращается. Последствия:
   - заставка, окно входа или диалог, показанные до главной формы, становятся «главными»: их закрытие завершает приложение, хотя главная форма открыта;

На Windows высоту строки встроенного шрифта меряет GDI, у него она больше. Значение оставалось в кеше `ThemeLineHeight` (ключ — семейство и размер), когда `uitest` выключал нативный рендеринг. На Linux и macOS у встроенных шрифтов нет нативного пути, поэтому там это не проявлялось. То же было бы в приложении, которое выключает `NativeFontRendering` в `main`.

   **Исправлено.** В ключ кеша добавлен `NativeFontRendering` ([theme_metrics.go](../ui/theme_metrics.go)). `uitest` после выключения вызывает `ApplyBaseFontSize`, чтобы пересчитать `DefaultUiLineHeight`. `DefaultUiLineHeight` у приложения, которое меняет `NativeFontRendering` после старта, по-прежнему пересчитывается только через `ApplyBaseFontSize`.

2. **Размер и место окна были внешней рамкой, а не клиентской областью.** `CreateWindowEx`, `Move` и `Resize` передавали размер в `SetWindowPos` как есть, то есть как размер с рамкой, а `WM_MOVE` и `WM_SIZE` сообщают клиентскую область. На Linux (с поправкой на `_NET_FRAME_EXTENTS`) и на macOS (`setContentSize`) это клиентская область. Последствия:
   - `form.SetSize(500, 300)` давал клиентскую область 484×261;
   - `RememberState`: каждый перезапуск смещал окно на рамку и уменьшал его на её размер;
   - развёрнутое окно создавалось с `WS_MAXIMIZE`, и `Move` до показа не задавал обычное положение: после перезапуска и «Восстановить» окно оказывалось в точке `CW_USEDEFAULT`, а в одном прогоне — почти во весь экран;
   - при сворачивании `WM_SIZE` 0×0 и `WM_MOVE` −32000 попадали в запомненное обычное положение, а `IsZoomed` у свёрнутого развёрнутого окна — false: закрытое свёрнутым, оно открывалось обычным размера экрана.

   **Исправлено** в [native_window_windows.go](../internal/platforms/native_window_windows.go) и [utils_windows.go](../internal/platforms/utils_windows.go):
   - размер и место пересчитываются через `AdjustWindowRectExForDpi` (`frameInsets`);
   - окно создаётся обычным и разворачивается при показе;
   - `WM_SIZE` с `SIZE_MINIMIZED` и `WM_MOVE` свёрнутого окна не меняют размер и место;
   - `IsMaximized` у свёрнутого окна смотрит `WPF_RESTORETOMAXIMIZED`;
   - `MoveToCenterOfScreen` центрирует окно вместе с рамкой.

   Проверено: клиентская область 500×300, перезапуск на том же месте; закрытое свёрнутым из развёрнутого открывается развёрнутым и восстанавливается в 500×300. `Move`/`Resize` развёрнутого окна (например, `SetSize` после `Maximize`) по-прежнему меняют его как есть, а не обычное положение.

3. **Строка с символом, которого нет во встроенном шрифте, рисуется без ClearType.** `systemFontFor` отдаёт GDI только текст, все символы которого есть в шрифте (`hasAll`). Иначе всю строку рисует растеризатор nui в оттенках серого. В приложении строка списка или таблицы с одним иероглифом, эмодзи или редким символом выглядит иначе соседних. Не исправлено: нужно делить строку на участки по шрифтам (GDI для своих символов, растеризатор nui для запасных) и согласовать с этим измерение, позиции курсора и базовую линию.

4. **Окна на мониторах с разным масштабом без конца перерисовывали друг друга, символы дёргались (все ОС).** Найдено вручную: лаунчер на мониторе 150%, notepad перенесён на монитор 100%. Масштаб, по которому меряется текст, был один на приложение, и его ставила каждая отрисовка окна (`setTextScale` в `processPaint`). При смене масштаба раскладывались заново и перерисовывались все формы, а перерисовка другого окна возвращала прежний масштаб. **Исправлено**: каждая форма меряет текст по масштабу своего экрана (`Form.useTextScale` в [text_scale.go](../ui/text_scale.go)). Масштаб ставится при входе в форму: `layoutNow`, таймер, `Form.Invoke`, отрисовка её всплывающих окон. Заново раскладывается только окно, которое само переехало на экран с другим масштабом. Кеш высоты строки хранит значение для каждого масштаба. Тест `TestWindowsOnScreensOfDifferentScales`: без исправления он видит по 6 лишних перерисовок у каждого окна. Текст, измеренный из другой горутины, меряется по масштабу формы, с которой UI-поток работал последней.

5. **Половинка суррогата, за которой не пришла вторая, оставалась и склеивалась со следующей одиночной нижней.** Последовательность `WM_CHAR`: `D83D`, `c`, `DE00` давала `c😀`, хотя `DE00` без пары должен отбрасываться. **Исправлено** ([utils_windows.go](../internal/platforms/utils_windows.go), `WM_CHAR`): верхняя половинка сбрасывается после любого символа.

6. **Окно Windows не становилось активным для nui при первом показе: `IsActive()` = false, `OnActivated` не вызывался, пока пользователь не переключался на другое окно и обратно.** `MoveToCenterOfScreen`, `Move` и `Resize` вызывали `SetWindowPos` без `SWP_NOACTIVATE`, поэтому окно активировалось прямо в `createWindow`, ещё скрытым, до того как форма подписалась на `WM_ACTIVATE`. `ShowWindow` активацию уже не повторял. Первая попытка, `hBalloonIcon`, ломала всё уведомление: Windows отвергает значок 32×32 без `NIIF_LARGE_ICON`, а 16×16 — с ним. Проверено программно, сообщениями в окно (`PostMessage`), без мыши:

- Вручную: печать через системный диалог (отмена, Microsoft Print to PDF, диапазон страниц), Export PDF в файл с кириллицей и пробелом в имени, открытие файла из папки с кириллицей. Страницы целые, кириллица и `中文` на месте, пока открыт диалог, окно не принимает ввод, после закрытия снова активно.

### IME на macOS (`ui.UseMacInputMethod`)

С 2026-10-29 включён по умолчанию (выключается `ui.UseMacInputMethod(false)`, в примерах — `NUI_MAC_IME=0`). Был новым кодом вслепую, выключенным по умолчанию. Клавиши идут через скрытый `NSTextView`, первый ответчик окна ([ime_darwin.go](../internal/platforms/ime_darwin.go)). Проверять на notepad (`go run . notepad`) и на однострочном TextBox (Edit → Find).

- [x] **Обычный набор без IME не сломан:** латиница, кириллица, цифры, Backspace, стрелки, Enter, Tab, Cmd+C/V/Z, выделение Shift+стрелки.
- [x] **Акценты по удержанию клавиши** (сначала не работали: удержание «e» печатало «eeee». Скрытое поле очищалось после каждого символа, а меню акцентов ищет букву перед курсором, чтобы заменить её. Теперь последний символ остаётся в поле, замена приходит в nui как Backspace и новая буква, поле очищается после клавиш, которые взял nui, и после щелчка; [ime_darwin.go](../internal/platforms/ime_darwin.go). Программно: `insertText:"é" replacementRange:` после «abe» дал «abé». Меню всё равно не появлялось: поле было спрятано через `alphaValue = 0`, а для полностью прозрачного поля система меню акцентов не показывает. Опыт: обычное `NSTextView` и наше поле, сделанное видимым, — меню есть в обоих. Теперь поле видимое, но текст, курсор и фон у него прозрачного цвета.)
- [x] **Option+буква не открывает меню** (было: Option+E в notepad открывал меню «&Edit» как мнемонику Alt+E, мёртвая клавиша не доходила до системы ввода). На macOS мнемоник меню нет: `menuMnemonics` выключен, подчёркивания не рисуются ([shortcut.go](../ui/shortcut.go)); тест `TestNoMenuMnemonics`, эталон `darwin/actions-menu.png`. (удерживать «e» → меню «é è ê…»): выбранная буква вставляется, меню стоит у курсора.
- [x] **Опция-сочетания с мёртвыми клавишами** (Option+E, затем E → «é»).
- [ ] **Китайский (Pinyin)** — пропущено в этом прогоне (нет раскладки): окно кандидатов у курсора; выбранные иероглифы вставляются; Esc отменяет набор без вставки; Backspace во время набора стирает в наборе, а не в тексте.
- [ ] **Японский (Kotoeri), корейский:** то же.
- [x] **Эмодзи из панели (Ctrl+Cmd+Space)** вставляются. (Сначала ничего не происходило: AppKit даёт этому сочетанию пункт «Emoji & Symbols» только в меню Edit главного меню, а у формы его обычно нет. Теперь скрытое поле само открывает панель, `orderFrontCharacterPalette:`, и выбранный символ приходит из поля; [ime_darwin.go](../internal/platforms/ime_darwin.go). Программно: синтетическое Ctrl+⌘+Пробел открыло панель, вставка «a😀b» в поле дала в nui 3 символа. Без `UseMacInputMethod` (теперь он включён по умолчанию) панели некуда вставлять символ. Вручную: эмодзи вставляется, но рисуется квадратиком — цветных шрифтов эмодзи растеризатор nui не умеет, см. «Найдено на macOS».)
- [x] **Щелчок по окну во время набора** не теряет фокус клавиатуры: после щелчка печать продолжается. Вручную (Option+E, щелчок в другое место, E): печать продолжается там, куда щёлкнули.
- [x] **Система ввода только в полях ввода.** Вручную в notepad: в тексте удержание «e» даёт меню акцентов, вне текста — нет, после возврата в текст — снова есть. Скрытое поле получает клавиши, только пока фокус в `TextBox` (`SetTextInputActive`, [ime_darwin.go](../internal/platforms/ime_darwin.go)); на кнопке, в списке, в таблице клавиши идут в nui напрямую: удержание буквы повторяет её, окно набора китайской раскладки не появляется. Начатый набор сбрасывается, когда фокус уходит из поля. Тест `TestTextInputActiveInTextBoxOnly`. Программно на macOS: фокус в поле — получатель клавиш `NUITextInputView`, на кнопке — `NUIPaintView`; удержанная «e» на кнопке в поле не попала; щелчок по полю возвращает ввод через систему.
- [x] Если всё работает — сделать `UseMacInputMethod` включённым по умолчанию. Включено 2026-10-29: акценты, мёртвые клавиши, эмодзи, обычный ввод проверены вручную; китайский, японский и корейский — нет. Вне полей ввода система ввода не участвует.
